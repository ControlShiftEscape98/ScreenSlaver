Part 2 of 4 · Superpowers Library
Engineering Process Skills
These skills (from the open-source Superpowers library) make me work the right way — methodically, safely, and efficiently. They trigger automatically based on what you're asking me to do.
💡
Brainstorming
brainstorming
Stops me from building the wrong thing by asking first.
Before I write a single line of code, this skill makes me slow down and ask you questions — one at a time — to fully understand what you actually want. It will offer 2-3 different approaches, explain the trade-offs, show you the plan in sections, and get your approval before moving forward. The goal: make sure we're solving the right problem, not just any problem.
💬 You might say…
"I want to add a new feature" "Help me plan this" "I have an idea, where do we start?"
🤖 Auto-triggers before any new feature or build
📋
Writing Plans
writing-plans
Breaks approved ideas into a step-by-step build checklist.
Once you approve a design from brainstorming, this skill creates a detailed implementation plan — a numbered list of tiny, 2-5 minute tasks, each with exact file paths, code snippets, and test commands. Think of it as a recipe. Nothing is vague. Every ingredient is listed. This makes the actual building phase fast and accurate.
💬 You might say…
"Looks good, let's plan it out" "Write the implementation plan" "Break this into tasks"
🤖 Auto-triggers right after a brainstorming session
🤖
Subagent-Driven Development
subagent-driven-development
Runs the build plan automatically with quality checks at every step.
Once the plan is written, this skill executes it. It launches fresh mini-agents for each task so they don't get confused by earlier steps, then runs two back-to-back reviews: one checking that the work matches the spec, and one checking that the code quality is good. Only when both reviewers say "✅ approved" does it move to the next task. This is what lets me work autonomously for long stretches without going off the rails.
💬 You might say…
"Go ahead and build it" "Execute the plan" "Let's go, start building"
🤖 Auto-triggers after a plan is approved
🧪
Test-Driven Development (TDD)
test-driven-development
Writes tests before code so bugs get caught immediately.
This skill enforces a strict rule: write a failing test first, watch it fail, then write the minimum code to make it pass. The test has to actually fail — otherwise it proves nothing. This catches bugs immediately rather than a week later in production. It also means every single feature has a test that proves it works, forever.
💬 You might say…
(No prompt needed — runs automatically inside the build)
🤖 Auto-triggers during every build task
🔍
Systematic Debugging
systematic-debugging
Finds the real cause of a bug instead of guessing.
When something breaks, this skill stops me from just randomly trying fixes. Instead it follows 4 strict phases: (1) investigate and find the root cause, (2) compare working vs broken code, (3) form one specific theory and test it minimally, (4) fix only that one thing. The stats behind this: systematic approach = 15-30 min. Random guessing = 2-3 hours of wasted work.
💬 You might say…
"Something is broken" "This isn't working, can you fix it?" "I'm getting an error" "The deployment failed again"
🤖 Auto-triggers on any bug, error or failure
🌿
Using Git Worktrees
using-git-worktrees
Creates a safe sandbox so new features never break your main code.
Before building anything, this skill creates a separate isolated workspace from your main codebase called a "worktree". Think of it like making a copy of your kitchen before trying an experimental recipe — if the experiment goes wrong, your original kitchen is untouched. When the feature is done and tested, it merges cleanly back in.
💬 You might say…
"Start a new feature branch" "Let's work on this without touching main"
🤖 Auto-triggers after a design is approved
👁️
Requesting & Receiving Code Review
requesting-code-review · receiving-code-review
Makes sure finished work is actually good before saying "done".
These two paired skills handle quality control. "Requesting" runs a pre-review checklist before handing off work — does it match the spec? are tests green? is anything missing? "Receiving" handles feedback — critical issues block everything until fixed, minor ones are noted. Together they create a built-in review loop that catches problems before they reach you.
💬 You might say…
"Review your own work before showing me" "Run a code review"
🤖 Auto-triggers between build tasks
🏁
Finishing a Development Branch
finishing-a-development-branch
Cleanly wraps up a feature and presents your options.
When all tasks are done, this skill verifies all tests pass, then gives you a clear choice: merge it into your main code, open a Pull Request, keep the branch for later, or discard it. It cleans up the worktree and leaves your project in a tidy state. No loose ends.
💬 You might say…
"We're done, wrap it up" "Merge this into main" "Task complete, what's next?"
🤖 Auto-triggers when all plan tasks are complete
⚡
Dispatching Parallel Agents
dispatching-parallel-agents
Runs multiple independent tasks simultaneously to save time.
When a plan has tasks that don't depend on each other (e.g., "build the login page" and "build the settings page" can happen at the same time), this skill launches multiple sub-agents to work in parallel. Instead of doing things one after another, multiple things happen at once. Dramatically cuts down build time on large features.
💬 You might say…
"Do all of these simultaneously" "Can you parallelize this?" "Run these tasks at the same time"
✋ Manual — you need to ask for it explicitly

Vector Memory (Pinecone)
vector-memory-pinecone
Semantic Memory & Search — compression that makes me smarter.
This skill provides long-term semantic memory. It uses Pinecone to store and retrieve "embeddings"—numeric representations of meaning. This allows for Retrieval Augmented Generation (RAG), lightning-fast semantic search through millions of data points, and context-aware grounding. It handles data chunking, hybrid search patterns, and automated memory management across Python and TypeScript.

Error Handling Patterns
error-handling-patterns
Heals broken code — finds, handles, and recovers from errors the right way.
This skill makes your apps resilient. Instead of crashing or silently failing, they catch problems gracefully, explain what went wrong clearly, and recover when possible. It covers: custom error hierarchies (Python, TypeScript, Rust, Go), retry logic with exponential backoff, circuit breakers that stop cascading failures, async error handling, graceful degradation, and how to write error messages that actually help. Every error gets handled at the right level — predictable, debuggable, production-ready.
💬 You might say…
"The app is crashing with an unhandled error" "Add proper error handling to this API" "The payment service keeps timing out" "Make this more resilient to failures" "Write better error messages for this feature"
🤖 Auto-triggers on errors, crashes, and resilience requests

How It All Flows Together
This is the natural order skills activate when you start something new.
Step 01
You have a rough idea
You describe what you want in plain language. I ask clarifying questions one at a time.
brainstorming
Step 02
We define the design together
I present 2-3 approaches, you pick one, we agree on the plan. I save the design doc.
brainstorming → writing-plans
Step 03
Safe workspace is created
A separate branch is made so the build never touches your working code.
using-git-worktrees
Step 04
Build begins, task by task
Mini-agents handle each task, writing tests first, then code. Reviewers check every task before moving on.
subagent-driven-development + test-driven-development
Step 05
Something breaks? Debugging kicks in
No random guessing. Root cause is found first, then one precise fix is applied.
systematic-debugging
Step 06
Feature complete — wrap it up
All tests pass. You choose: merge, PR, keep, or discard. Clean finish every time.
finishing-a-development-branch
